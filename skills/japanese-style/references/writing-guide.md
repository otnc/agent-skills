# 文章の組み立てと表記

日本語で判断材料や作業手順、結果を伝えるときのガイド。文体や形式の指定がある場合は、その指定を優先する。雑談、相談、創作、翻訳では、相手や原文に合う口調や表現を選ぶ。引用は原文の表記を保つ。

## 回答の組み立て

- 質問への回答は、答えや推奨する操作を冒頭に置く。判断が条件で変わる場合は、条件ごとの答えを出す。たとえば「共同編集するなら共有ドキュメントに書く。提出先が PDF を指定しているなら、提出時に PDF に書き出す」と書く。
- 読み手が次に作業できるように、必要な前提、判断基準、例外や手順を書く。質問を繰り返す前置きや、本文を言い直しただけの結びは省く。次の操作や確認事項がある場合は、最後に具体的に示す。
- 一文が60字を超えたら、条件、結論、理由がどこにかかるか見直す目安にする。複数の説明が重なっていれば文を分ける。段落の長さは内容のまとまりで決める。並列する選択肢は箇条書きや表にできる。因果関係は文でつなぐ。
- 依頼の読み方が複数あるときは、採用した前提を必要に応じて示す。読み方次第で判断が変わるなら、条件ごとに答えるか、判断に必要な点を具体的に尋ねる。
- 変更後の文章やコードを回答に載せる場合は、必要な見出し、項目、関数など、コピーして使える単位で示す。省略した箇所が前後の意味や使い方に関わるなら、どこを省いたか明示する。

## 主語と述語

- 主語は、読み手が同じ動作主を特定できる範囲で省く。動作主が変わるとき、受け身や使役で人とシステムのどちらが処理するか曖昧なとき、コメントや項目が単独で読まれるときは、必要な名前を出す。読者向けの手順では、動作主が読者だと明らかなら省いてよい。
- 目的や条件は、何をするのか分かる動詞で書く。「［処理名］用に変更」のように読み方が分かれるなら、「［条件］でも［操作］できるように、［対象］を変更した」と書く。理由が複数の操作にかかるように読めるときは、対応する操作の近くに置く。
- 不具合は、欠けている動作が伝わる述語で書く。たとえば「入力が空でもテストは通る」だけで意図が伝わりにくい場合は、「フォームが空の入力を受け付ける不具合を、このテストでは検出できない」と書く。
- 対象と動作が曖昧な擬人化や比喩は、読み手が確認できる条件や結果に置き換える。「保存が黙って失敗する」なら、確認できた範囲で「保存に失敗しても画面にエラーが表示されない」と書く。「関数が値を返す」のような定着した技術表現や、依頼されたたとえはそのまま使える。

## 事実、数値、確認範囲

- 観測した結果には、判断に必要な環境や条件を添える。推測には、推測の根拠と確かめる方法を書く。結果が得られていない場合は、どこまで試したかが分かる言い方にする。
- 調べた数値は出典や計測条件を示す。計算した数値は、読み手が追試できるように、必要に応じて式、単位、丸め方を添える。推敲や要約では、元の数値、比較対象、条件、確かさを保つ。
- PR や wiki では、途中の作業をあとから引き継げるように書く。未確認事項を残す場合は、誰が確認していないかより、何をどの環境で確かめるかが分かる文にする。コミットメッセージとコードコメントは、変更の内容や理由など、その場所で後から役に立つ情報に絞る。

## Markdown と和文の表記

- 太字は、リストの項目名、初出の用語、画面のボタン名など、目で探す短い語句に使う。文全体を強調したくなったら、結果を前へ出すか、述語で重要度を伝える。コード、コマンド、ファイル名はインラインコードで示す。プレーンテキストでは、Markdown の装飾に頼らず順序や言葉で伝える。
- 太字の前後に括弧や句読点があるときは、原則として記号を太字の外へ置く。画面のラベルや正式名称に記号が含まれる場合は、原表記を保ち、意図どおりに表示されるか確認する。
- 丸括弧やダッシュで長い補足を挟むと主文を見失いやすい。理由や前提は文を分け、箇条書きの詳しい条件は子項目にする。略語は必要なときに初出で説明する。
- 日本語と英字の間の空白は、対象の文書やリポジトリの書き方に合わせる。日本語と英字が続く箇所の空白を詰める方針でも、英語名に含まれる空白、コード内の空白、Markdown の区切りは保つ。
- URL を単独行で示すなら、末尾に句読点を付けず、リンク部分が分かるように置く。本文では、リンク先の内容が分かるリンク名を使う。

## 図表と数式

- 図や表には、単独で見ても何を示すか分かる題を添える。対象、指標、単位、期間、比較条件のうち、読み取りに必要なものを書く。たとえば「表1 端末別の初回表示時間（ms、各10回の中央値）」のように示す。
- 本文から参照する図や表には番号を付ける。「上の表」のような位置で指す表現は、配置が変わる文書では番号に置き換える。キャプション欄があれば使う。指定のない場合は表の上、図の下を目安にする。
- 数式は、LaTeX が使える媒体なら数式として表示する。コードコメントやコミットメッセージなどでは、`rate = count / seconds` のようにプレーンテキストでも読める形で書く。

## 仕上げの確認

- 冒頭で質問に答え、判断や作業に必要な条件を示しているか。
- 誰が何をしたか、どの語句が何にかかるかを、読み手が迷わず判断できるか。
- 比喩や抽象語で、何が起きたかを読み手に推測させていないか。
- 数値や確かさが根拠と合っているか。図表には単位など、読み取りに必要な情報があるか。
- 説明と手順がつながっているか。強調を外しても内容が伝わるか。
