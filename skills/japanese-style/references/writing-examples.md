# 日本語の修正例

## 会話と進捗報告

想定する場面は日本語のやり取りの途中で CI が `Error: Missing environment variable API_URL` を返したとき。

- 修正前「The CI job failed because API_URL is missing.」
- 修正後「CI は `API_URL` が未設定で止まったよ。ログには `Error: Missing environment variable API_URL` と出ている。」

原因の説明は会話の言語に合わせる。ログは読み手が同じエラーを検索できるよう原文を引用する。

設定方法を聞かれたら必要な操作から答える。操作が環境によって変わる場合はどの環境に当てはまるかを同じ段落に書く。

- 修正前「環境に応じて、適切な設定をしていただく形になります。」
- 修正後「ローカルでは `.env` に `API_URL` を設定してね。CI ではジョブの環境変数に設定するよ。」

## ドキュメント

既存の README が「です・ます」調で、同じ処理を「リクエスト」と呼んでいる場面。

- 修正前「要求の送信前に、設定値の確認を行う。」
- 修正後「リクエストを送る前に設定値を確認します。」

文末と用語は周囲の文章に合わせる。「確認を行う」は「確認する」で動作が伝わる。

技術文書では状態の変化を読み手が確かめられるように書く。たとえばキャッシュを消す操作が完了したら、次の読み込みでサーバーからデータを取得する仕様の場合。

- 修正前「キャッシュの削除で、読み込みがリセットされます。」
- 修正後「キャッシュを削除すると次の読み込み時にブラウザーがサーバーからデータを取得します。」

比喩や語義から外れた動詞で書いた不具合は観測した変化に置き換える。スタイルシートを差し替えたあとに画面を確認した場面。

- 修正前「CSS を入れ替えるとレイアウトが壊れる。」
- 修正後「CSS を入れ替えるとカードの幅が広がって右端のボタンが画面の外に出る。」

## コードコメント

同じ ID に対する重複処理を防ぐため、リクエストを送る前に処理済みの ID を確認する場面。

- 修正前「処理済みの ID を確認する。」
- 修正後「リトライ時に同じ ID のリクエストを二重送信しないため処理済みか確認する。」

処理の理由がコードだけでは読み取りづらい場合はどの条件で何を防ぐのかを書く。

複数の処理が続く場合は担当が変わる場所で名前を出す。

- 修正前「保存に成功すると通知して一覧を更新する。」
- 修正後「保存に成功するとサーバーが完了イベントを送る。イベントを受け取ったクライアントが一覧を再取得する。」

## 結論と要約

手元で障害を再現しようとしたが再現せず、修正は入れていない場面。

- 修正前「不具合は解消しました。」
- 修正後「手元の環境では不具合を再現できませんでした。」

要約では確認した環境と結果が伝わるように書く。

授業での生成 AI の利用状況と課題の提出率を前期と後期で比べた資料を要約する場面。

- 修正前「生成 AI は使う、でも差は広がる。」
- 修正後「後期は生成 AI を使う学生が増えた。ただし使う学生と使わない学生の課題提出率の差は前期の5ポイントから後期の12ポイントに広がった。」

比べる名詞には何と何をどの軸で比べたかを書き、節ごとに主語を書く。差の値は資料で確認できたものだけを書く。

PR の説明にはあとから確認を引き継げる情報を残す。

- 修正前「まだ自分では確認できていません。」
- 修正後「未確認の項目はキャッシュ削除後のオフライン表示です。ネットワークを切断して再読み込みし、案内が表示されることを確認してください。」

## コミットメッセージ

組織で日本語のコミットメッセージを使っていて、入力値が空のときに保存できないよう修正した場面。

- 修正前「保存の挙動をいい感じに修正」
- 修正後「fix: 名前が空のときにプロフィールを保存できないようにする」

接頭辞はプロジェクトの規約に合わせる。本文には変更した操作や条件を書く。
