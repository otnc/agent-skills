# 日本語の文章

日本語で書く部分は、読み手や媒体に合わせて、意味をすぐに取れる文章にする。英語のコードやログを読んだあとも、日本語の指定がある進捗、レビュー、結論は日本語で書く。引用するログ、コマンド、識別子は元の表記を保つ。

## 文体と表記

- 会話では相手との距離に合う口調を使う。ドキュメントやコメントを編集するときは、周囲の文体と表記に合わせる。対外文書は相手との関係に合う敬語を使う。
- 地の文の句読点は、指定や既存の表記規則がなければ「、」「。」を使う。数字、括弧、送り仮名、用語の表記は、同じ文章の中で意味や用途が同じならそろえる。改行は段落や項目の切れ目に置く。
- 英語などから移した文で、修飾先や誰が何をしたかが曖昧なら、語順を整えるか必要な主語を補う。要約や推敲では、元の数値、条件、確かさを保ったまま読みやすくする。

文体や直し方に迷ったら、[会話・ドキュメント・コメント・要約の修正例](references/writing-examples.md) を見る。

## 用語の決め方

1. ユーザーが指定した表記や、対象プロジェクトの用語集・既存ドキュメントに従う。画面のラベル、正式名称、直接引用、コマンド、API の識別子は元の表記を保つ。
2. 表記の指定がない場合は、読み手がその対象を会話や検索で何と呼ぶかを考える。ユーザーの言い方、周囲の文章、製品やライブラリのドキュメントが手がかりになる。略語や英字表記が定着している場合は、`PR` や `HTTP` のようにそのまま使える。
3. 「日本語で」と指定されても、分野で定着しているカタカナ語は、用語例に載っていないものも含めて使う。カタカナ語のほうがすぐに通じるなら、和語や漢字の熟語への置き換えは不要。既存の文に直訳があれば、何を指すか確かめてから普段使われる表記に戻す。
4. 読み手に通じる日常語も使う。たとえば一般向けの案内なら「設定を更新する」、書籍なら「第2版」が自然。初めて出てくる専門用語を読み手が画面やドキュメントで探す必要があるなら、その用語を残して初出時に短く説明する。

## 用語と文字のチェック

迷ったときや、既存の技術文書に直訳が続くときは、[技術用語の例](references/terminology.md) を見る。各行は使い分けの例で、対象や操作を確かめてから適用する。

送信前に、見出し、箇条書き、結論で用語が変わっていないか確認する。同じ対象には同じ呼び方を使い、「前の版へ戻した」のような短いまとめでも、ソフトウェアの話なら「前のバージョンに戻した」と書く。

Node.js が使えるなら、新規・編集した日本語の文章を [lint.js](scripts/lint.js) で確認できる。技術用語は `--terminology`、部首記号は `--kangxi-radicals`、文字化けは `--encoding` を選ぶ。複数のオプションを指定できる。省略すると全項目を調べる。

以下はスキルのディレクトリから UTF-8 のファイルを調べる例。会話やメッセージの下書きを標準入力から渡すときは、ファイル名の代わりに `-` を指定する。

```sh
node scripts/lint.js --terminology article.md
node scripts/lint.js --kangxi-radicals article.md
node scripts/lint.js --encoding article.md
```

- `warn [terminology]` はカタカナ語にできるかを確かめる候補。使い分けが適切な語や意図的な表記は残す。用語例にないカタカナ語にも「用語の決め方」を適用する。
- `error [kangxi-radical]` は部首記号が見つかった箇所。普通の文章に紛れ込んでいたら文脈に合う漢字に直す。部首の説明や直接引用で意図的に使う場合はその文字を保つ。[康熙部首214字の対応表](references/kangxi-radicals.md)
- `error [encoding]` は不正な UTF-8 のバイト列か、入力に含まれる置換文字（U+FFFD）。不正なバイト列なら、元の文字コードを確かめて読み直す。置換文字が意図せず入っていたら原文と照合して直す。引用や説明で意図して使った置換文字は保つ。

見た目が同じなのに検索や置換が一致しないときは、元の文字列を取り出してコードポイントを確かめる。置換対象には元ファイルの文字列を使い、修正が必要な箇所に絞って直す。
